## 1. 表关联逻辑反思

### 1.1 正确的主外键拓扑

```
                    ┌──────────────────────────┐
                    │  customers (原始 99,441) │
                    │  PK customer_id          │
                    │  ── customer_unique_id   │  ← 客户级主键藏在这里
                    │  ── zip_prefix / city / state
                    └───────────┬──────────────┘
                                │ 1 : 1（每单一个 customer_id）
                                │ 关联键：customer_id
                    ┌───────────┴──────────────┐
                    │  orders (99,441)         │
                    │  PK order_id             │
                    │  FK customer_id          │
                    └───┬──────────┬───────────┘
                        │ 1:n      │ 1:n
          ┌─────────────┴──┐   ┌───┴──────────────┐
          │ order_items    │   │ payments / reviews│
          │ PK(order_id,   │   │ PK order_id(聚合后)│
          │    order_item_id)  └──────────────────┘
          └───────┬────────┘
                  │ n:1
          ┌───────┴────────┐
          │ products       │
          │ PK product_id  │
          │ FK category ───┼──> translation（带 BOM，须 utf-8-sig）
          └────────────────┘

          独立维度：
          geo_prefix (PK zip_code_prefix) ←── customers.zip_prefix（n:1，已聚合去重）
          customers_clean (PK customer_unique_id) ←── 由 orders ⨝ customers 聚合而来
```

### 1.2 桥接关系：`customer_id` 与 `customer_unique_id`

这是整个项目最容易错的一处，必须分清：

| 字段 | 所在表 | 粒度 | 作用 | 能否用来算客户指标 |
|---|---|---|---|---|
| `customer_id` | orders、customers | **订单级**（每单一个，同一人多次下单会不同） | 订单 ↔ 客户表的**桥接键** | ❌ 不能。用它算 F 会得出"人人只买一次" |
| `customer_unique_id` | **仅 customers** | **客户级**（同一人始终相同） | 客户维度的**真正主键** | ✅ 只能用这个 |

**桥接动作**（必须先做，再做任何客户聚合）：

```
orders ──(customer_id)──> customers ──> 取出 customer_unique_id ──> 才能 groupby 客户
```

一句话记法：**`customer_id` 是"这一单是谁下的"，`customer_unique_id` 才是"这个人是谁"。**

### 1.3 两条链路必须独立（Bug 2 的根因）

```
链路 A（明细维表）
  customers(原始) ──> 取 zip/city/state ──> 与 orders 按 customer_id 关联 ──> orders_clean
                                              ↑
                                    这里要的是原始 customers（有 customer_id）

链路 B（客户维表）
  orders ⨝ customers ──> groupby customer_unique_id ──> cust ──> customers_clean
                                              ↑
                                    这里要的是聚合结果（有 customer_unique_id）
```

两条链路**共用源表但产出物不同**，谁也不能替谁。把 `cust` 传给链路 A 会报"找不到 customer_id"；把原始 `customers` 传给链路 B 会导致一个客户出现多行（一单一行）。

### 1.4 三个 Bug 的根因归类与防复发规则

| # | 现象 | 根因类别 | 防复发规则（写代码前先默念） |
|---|---|---|---|
| 1 | `build_customers` 直接对 orders 按 `customer_unique_id` 去重 → KeyError | **字段归属错误**：以为 orders 表有客户级 ID | 写任何 `groupby`/`merge` 前，先确认该字段**在哪张表**，不确定就先 `print(df.columns)` |
| 2 | `build_orders` 传入聚合后的 `cust`（无 `customer_id`） | **传参错位**：同名变量两种形态 | 变量名带语义：`customers_raw`（原始）与 `cust_dim`（聚合），禁止都叫 `cust` |
| 3 | `dt.dayofweek` 弃用警告 | **API 演进** | 升级 pandas 后先扫一遍 `.dt.` 与 `.str.` 访问器；警告不等于可忽略 |

**由此提炼的三条通用规则**

1. **先看列、再写码**：任何 merge 之前，确认左右两表的键**同时存在且同名**。
2. **一个变量一个形态**：原始表与聚合表用不同变量名，杜绝"传错版本"。
3. **报错优先于将错就错**：本轮最危险的其实不是报错（会立刻发现），而是 **BOM 导致的静默失配**——不报错，但品类英文名整列变 `unknown`。凡是 merge 后某列突然大面积为空/为默认值，先怀疑键值不匹配，而不是数据本身。

## 2. 关键指标锁定（后续论文与建模的基准）

### 2.1 三个基准值（锁定，不再重算）

| 指标 | 数值 | 定义 | 适用场景 |
|---|---|---|---|
| **主分析集订单数** | **97,308** 单 | `orders_clean` 行数：delivered+shipped 且 2017-01-01~2018-08-31 | 全文所有"订单量"表述的基准 |
| **唯一客户数** | **96,096** 户 | `customers_clean` 行数（`customer_unique_id` 去重） | 全文所有"客户数"表述的基准 |
| **复购率** | **3.12%** | 下单 ≥2 次的客户 ÷ 全部客户 | 客户资产结构的核心结论 |

### 2.2 一致性校验（已核，全部自洽）

| 校验项 | 计算 | 结果 | 判断 |
|---|---|---|---|
| 主分析集保留率 | 97,308 ÷ 99,441 | **97.86%** | 合理（仅剔除 2016 年稀疏期与 2018-09 后截断期） |
| 复购率是否越过上界 | 3.12% vs 3.48% | **低于上界** | 自洽（上界＝额外订单数÷客户数，实际复购户数必小于它） |
| 复购户数推算 | 96,096 × 3.12% | **≈2,998 户** | 与 3.48% 上界对应的 3,345 户相容 |
| 额外订单分解 | 99,441 − 96,096 = **3,345** 笔非首单 | 2,998 户各贡献 1 笔 ＋ **347 笔**来自 3 单及以上客户 | 完全闭合 |
| 人均订单（全量） | 99,441 ÷ 96,096 | **1.035 单/人** | 与 3.12% 复购率一致 |
| 评价表差异 | 原始 98,673 单有评价 → clean 98,128 | 少 **545** 单 | 与 547 个"一单多评"订单量级吻合，见 §4 |

> 结论：**三个基准值互相印证，可以作为论文的"数据概况"段落直接引用**。3.12% 这个数字本身就是最重要的商业洞察起点——它说明 Olist 是典型的一次性交易平台，任何"提升复购"的建议都必须先解释这个基线。

### 2.3 引用纪律（避免全文数字打架）

- 论文、图表标题、结论段落**统一引用同一组数**，不在各章节各自重算。
- 凡出现"约""近"等模糊词，一律给出基准值再修饰，例如"复购率仅 3.12%（约 3 千户）"。
- 若后续因模型口径需要子集（如 RFM 只算有支付记录的订单），**必须显式标注"有效订单 97,3xx 中的 xx,xxx 单"**，不能悄悄换基数。

## 3. `03_rfm.py` 代码审查清单

### 3.1 读入层

| # | 检查项 | 具体要求 |
|---|---|---|
| R1 | 编码 | `pd.read_csv(..., encoding="utf-8-sig")`，**读写都用**；用 `utf-8` 会让首列名带 BOM |
| R2 | 路径 | 只用相对路径 `data/clean/orders_clean.csv`，不写绝对路径 |
| R3 | 类型 | `customer_unique_id` 读为 string；日期列 `pd.to_datetime(errors="coerce")` |
| R4 | 只读 | 不修改 `data/clean/` 下任何文件，输出另存 `outputs/tables/` |

### 3.2 客户口径（最高危）

| # | 检查项 | 具体要求 |
|---|---|---|
| R5 | **粒度** | `groupby("customer_unique_id")`。**绝不能用 `customer_id`**——orders_clean 里它是订单级的，用它算 F 会得到 100% 单次购买 |
| R6 | **数据源** | 从 `orders_clean` 聚合，**不要从 `customers_clean` 出发**：后者含 2016 年首购、窗口外客户，会把不属于主分析集的人算进 RFM |
| R7 | 客户数断言 | `rfm` 客户数应 **≤ 96,096**，并打印实际值。若等于 96,096 反而要警惕——说明没做窗口过滤 |
| R8 | 空客户 | merge 后 `customer_unique_id` 为 `unknown` 的行必须为 0，否则断言失败 |

### 3.3 R / F / M 计算细则

| # | 指标 | 口径 | 易错点 |
|---|---|---|---|
| R9 | R | 快照日 ＝ `orders_clean.order_purchase_timestamp.max()` **+ 1 天**；R ＝ 快照日 − 该客户最后一次下单日（天） | 快照日必须显式打印并写进论文；用"今天"会让结果随运行日期变化，不可复现 |
| R10 | F | `nunique(order_id)` per 客户 | 不能用 `count()`（会被一单多商品放大）；不能对 items 表计数 |
| R11 | M | `sum(payment_total)` per 客户 | 只取一个来源（payments 汇总），不要与 `item_value_total` 相加 |
| R12 | 无支付订单 | 先剔除 `has_payment == False` 的订单再算 M | 不剔除会让个别客户 M=0 被误判为低价值 |
| R13 | R 的方向 | **R 越小＝越近＝越优质**。八分类命名与排序时方向**不能反** | 这是 RFM 最常见的逻辑反转错误 |

### 3.4 切分与八分类

| # | 检查项 | 具体要求 |
|---|---|---|
| R14 | R/M 切分 | 用**中位数**（金额与频次右偏，中位数抗极值）；切分阈值必须打印出来写进论文 |
| R15 | F 切分 | **不用中位数**（复购率 3.12%，中位数恒为 1，二分会让全部客户落到同一侧）；用业务断点：`1 单` vs `≥2 单` |
| R16 | 八分类 | 2(R) × 2(F) × 2(M) = 8 类；命名可读，如 `R高F低M高`，并给出中文释义（重要价值/一般保持/流失预警…） |
| R17 | 分布披露 | 必须输出 8 类的**客户数与占比**。预期 4 个"F高"类合计仅约 3%，单类不足 1%——这是真实结构，不许为图好看而合并或剔除 |
| R18 | 退化说明 | 论文需写明"F 维度因平台复购率极低而近似二值，八分类实质退化为 R×M 四象限的细分"，并把这句作为洞察而非缺陷 |

### 3.5 输出与自检

| # | 检查项 | 具体要求 |
|---|---|---|
| R19 | 输出表 | `rfm.csv`（客户级：customer_unique_id, R, F, M, R_score, F_score, M_score, segment）＋ `rfm_summary.csv`（八类汇总：客户数、占比、GMV、客单价） |
| R20 | 主键唯一 | 断言 `rfm.customer_unique_id` 唯一 |
| R21 | 合计校验 | `rfm.M.sum()` 应 ≈ `orders_clean[has_payment].payment_total.sum()`，误差 <1 元；不等说明有客户被漏掉或重复计入 |
| R22 | 复购率交叉 | 从 rfm 重算的复购率会**略低于 3.12%**（窗口过滤把"2016 首购+2017 复购"的人截成单次购买）。这是预期偏差，须在论文注明，**不得为了对上 3.12% 而放宽窗口** |

### 3.6 跑完必须核对的五个数

1. RFM 客户数（应 ≤ 96,096）
2. 八类客户数合计 ＝ RFM 客户数（不能丢人）
3. `rfm.M.sum()` 与支付总额是否一致
4. 复购率（应 ≤ 3.12%，并解释差异）
5. 快照日（须与 `orders_clean` 最大下单日相差 1 天）
